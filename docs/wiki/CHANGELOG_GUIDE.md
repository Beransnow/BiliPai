# 更新日志撰写规范

最后更新：2026-08-04

## 基准与信息来源

1. 使用 `gh release list` 确认 GitHub 上一个实际发布标签，不把只有 Changelog 记录、没有 Release 的中间版本作为基准。
2. 使用 `git log <previous-tag>..HEAD --oneline` 获取完整提交范围，并结合代码差异确认最终行为。
3. 合并提交与其子提交只归纳一次；回滚后已不存在的行为不写入发布说明。
4. 优先描述用户能获得什么、问题如何改善，避免把类名、函数名或机械提交标题直接堆给用户。

## 固定格式

```markdown
## v<versionName> (YYYY-MM-DD)

### 版本信息

- 从 `<previous-version>` 升级到 `<versionName>`，`versionCode` 升级至 `<code>`。
- 安装、数据迁移或兼容性说明；没有特殊事项时可写“无需迁移用户配置”。

### 更新范围

- 基准版本：GitHub 上一个正式发布版 `<previous-tag>`。
- 提交范围：[`<previous-tag>...<current-tag-or-main>`](GitHub Compare URL)。

### 完整更新

#### <用户可理解的功能领域>

- <新增能力及其使用结果>。
- <重要修复及其改善结果>。

#### 版本与发布

- <版本、安装包、更新兼容或发布流程变化>。

### 已知事项（可选）

- <仍存在且用户需要提前知道的限制或一次性操作>。
```

## 撰写规则

- “完整”指覆盖比较区间内所有有实际结果的提交主题，不要求逐条列出每个提交。
- 每个领域通常写 1 至 5 条，每条只表达一个主要结果；相同功能的多次修复合并成一条。
- 建议顺序：核心改版、内容与播放、页面体验、修复、版本与发布；没有变化的领域不保留空标题。
- 新功能使用“新增/支持”，行为调整使用“优化/调整”，问题修复使用“修复”；不使用“史诗级”“完美”等无法验证的宣传词。
- 内部重构、测试和依赖升级只有在影响稳定性、兼容性或开发交付时才单列说明。
- 安装方式、账号数据、设置默认值、权限、版本纪元或 APK 名称发生变化时，必须在“版本信息”或“已知事项”中明确写出。
- 发布前把 Compare 链接中的 `main` 换成正式标签，并再次确认标签、`versionName`、Changelog 与 APK 文件名一致。

## 发布前核对命令

```bash
gh release list --repo jay3-yy/BiliPai --limit 10
git log <previous-tag>..HEAD --oneline
git diff --stat <previous-tag>..HEAD
```

上述命令只用于确定事实；最终文案仍需按实际用户行为归类，并删除重复、已回滚或仅存在于开发过程中的描述。
